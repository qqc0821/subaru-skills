# subaru-slides 中文技术汇报优化方案

日期：2026-09-14。状态：建议方案，尚未实施运行时改动。

## 1. 建议定位

下一版专注于**中文技术工作汇报的原生可编辑 PPTX**，先把程序员年度述职做成稳定基准，再扩展到项目复盘和季度技术汇报。

默认服务对象是技术负责人和管理者；核心问题是：承担了什么目标、解决了什么问题、个人贡献是什么、结果有什么证据、下一步怎样改进。视觉采用一套克制的浅底技术报告设计系统，按内容选择版式。

品牌模板继续作为输入约束保留。漫画、全页 AI 图片、HTML deck、艺术风格探索退出默认流程。能力不足时明确说明可交付范围；不能把图片 PPTX 当作可编辑交付。

## 2. 审查依据与判断边界

当前 skill 有 48 个 Markdown：入口 1 个、参考文档 24 个、风格 preset 23 个。参考文档共 1272 行，preset 共 1100 行。17 张 WebP 样例共 1,087,492 字节。

这些文件不会因为存在就全部进入模型上下文。应优化实际加载链、规则一致性和执行能力，不能把文件多直接当成质量差的原因。

| 发现 | 对生成质量的影响 |
|---|---|
| 入口同时路由 A/B'/C/B/fallback，A 排第一，B' 又标为推荐默认 | 默认执行方向不唯一 |
| 内容指南主要是标题、要点、视觉类型，没有技术述职的贡献与证据字段 | 容易生成通用工作总结，难区分工作量和实际价值 |
| 23 个 preset 中 6 个没有样例，包括数据叙事、瑞士网格等正式方向 | 风格名称和提示词尚不能证明目标场景的成品质量 |
| 抽看的 blueprint、whiteboard-sketch 样例均为消费营销转化主题 | 可参考画风，不能验证技术成果页、复杂架构页或全册节奏 |
| 原生路径只有泛化 API 示例，并指向当前不存在的历史构建文件 | 关键版式仍依赖模型临场实现；内置 helper 主要装配图片 |
| 正文规范分别出现 ≥24pt、≥18pt、10–13pt，同时多处要求标题正文 3:1 | 缺少统一且适合中文投影阅读的尺寸标准 |
| eval 主要检查页数、对象、中文字符、字体、路径等 | 能验证结构，不能证明事实可靠、叙事清楚或视觉优秀 |

尚未查看用户反馈较差的 PPT、原始素材及生成记录，因此不能确定具体失败由哪些因素造成，也不据此评价某个模型。

## 3. 内容收敛：建立技术成果证据链

每个候选成果先整理为：目标与背景 → 问题与约束 → 个人行动及关键取舍 → 结果证据 → 团队/业务影响 → 局限与后续。

同时记录数据来源、时间范围、指标口径和个人职责。区分团队成果与个人贡献，区分已实现结果与下一年目标；缺失数据标记待补充，不能编造提升百分比。无量化材料时可用上线记录、验收结果、故障复盘或采用情况等定性证据。

逐页大纲字段改为：本页结论、支撑证据、个人贡献、展示方式、来源、缺口。优先处理受众、时长和关键证据缺口，不让用户先理解构建路径或选择三种画风。

年度述职的可调整结构：年度结论 → 职责与目标 → 2–3 个重点项目 → 质量/效率改善 → 协作与知识沉淀 → 问题复盘 → 下一年优先级。页数服从材料和汇报时长，不强填固定页数。

例如，“持续赋能系统稳定性”应改成与材料一致的具体结论。若材料确实支持，可以写“完成核心链路超时治理，峰值期故障减少”；只有在基线和统计口径齐全时才补数字。

## 4. 视觉收敛：一套设计系统，多种信息版式

默认浅色背景、深色文字、单一强调色；品牌输入可覆盖配色和字体。停止默认提供三个风格方向，先直接制作成果页、图表页、复杂技术页，检查真实内容承载能力。

优先实现 8 类可复用原生版式：封面与年度结论、成果总览、项目深挖、前后对比、趋势与指标、技术架构/流程、问题复盘、行动计划。

版式按信息关系选择，避免全册变成相同的三卡片。图表呈现比较与趋势，架构图解释系统关系；纯文字结论页可以存在，取消“每页必须加视觉元素”的机械要求。

以 16:9 投影为首个验收场景：标题建议 30–36pt、正文 20–24pt、辅助说明 14–16pt，作为初始设计值经渲染修正。关键证据不能藏在小字中；内容放不下时优先删改、拆页或放入备注，不自动缩小正文。不再要求标题正文固定 3:1。

## 5. 文件与语言处理

| 当前内容 | 建议处理 |
|---|---|
| SKILL.md、workflow、content-structure、writing-quality | 入口只保留唯一流程；后三者合为中文汇报内容指南 |
| design-principles、typography-cjk、design-system | 提取并合为一份中文排版规范，删除重复色板、趋势罗列和冲突规则 |
| path-a-native、native-evidence、dependencies | 合为构建指南，配真实可运行的原生构建实现和能力探测 |
| qa 下三份文档 | 合为验收与交付指南，分别检查事实、结构、视觉与可编辑性 |
| template-following | 保留为提供品牌模板时按需加载的文档 |
| gallery、design-movements、Snoopy 经验、旧艺术 preset 和样例 | 从默认加载和安装包移出；先保留在历史版本或仓库扩展目录，不急于批量删除 |
| integrations、harnesses、speaker-notes 等 | 必要运行时信息并入对应指南，其余进入维护文档或按需扩展 |

目标是入口加约 5 份职责清晰的参考文档；这是组织目标，不能为凑数量把不同职责重新堆成长文。入口建议控制在 100 行左右，所有信息只维护一个权威位置。

自然语言规则、标题、示例、错误提示及默认输出统一简体中文；路径、标识符、JSON key、API 名称保持英文。必要专业术语保留原文。不做一中一英重复说明，不默认加 INSIGHT/TAKEAWAY 等英文装饰标签。

将英语“每行不超过 5 个词”等规则替换为中文文本框宽度、行数和渲染检查。语言统一便于理解和维护，但本身不构成质量提升证据。

## 6. 补齐可执行能力与有效样例

建立一套有运行证据的原生构建参考实现，包含上述版式、中文字体检测、文字测量、图表单位及原生备注。新增构建脚本的必要性是减少模型临场猜测布局与 API；复用现有可选依赖并提供自检，不绑定任何外部 skill。具体依赖选择在实施阶段先探测再决定。

样例改为同一份中文技术汇报固定材料生成的关键页，配结构化输入和生成源码，使预览与实际构建结果一致。优先补成果页、数据页、技术架构页、复盘页，而非继续增加漂亮封面。

不把“存在一张样例”称为效果已验证。成熟度证据至少区分：有预览、有可复现构建、完成目标场景评测。

## 7. 验收：用同条件比较证明改善

先保留旧版基线，再比较“仅精简文档”和“精简 + 证据链 + 可执行版式”两个阶段，观察改善来自哪里。固定模型、原始材料、输出要求、可用工具及运行参数，记录实际加载文件和人工修改量；每组至少运行 3 次，不以一次最佳结果代表稳定性。

首批用例：材料完整的年度述职、缺少指标的年度述职、复杂架构项目复盘。失败案例取得后纳入首批基准；可先用明确标注为虚构测试材料的固定 brief 建立流程。

建议评分为内容与证据 40%、叙事 25%、视觉可读性 25%、可编辑和交付 10%。顺序打乱后盲评，记录评分理由和修改成本。总分 80/100 可作为初始目标，后续由用户实际满意度校准。

硬门槛：不得编造事实或个人贡献；无严重溢出和缺字；承诺可编辑的文字、图表及表格必须可编辑。事实溯源需逐项核对，不能用中文字符数或模型自评分代替。视觉验收逐页查看渲染图，整册缩略图检查节奏。

保留 make check 与必要单测，新增场景评测补充现有结构检查。若缺少渲染器或原生构建能力，明确记录未验证范围，不记作通过。

## 8. 实施顺序

1. **P0：建立基线并收敛默认行为。** 固定技术述职 brief，保留旧版结果；重写中文入口与内容指南，取消默认风格三选一，统一字号和标题规则。
2. **P1：完成可编辑版式。** 实现并渲染 8 类版式，补目标场景样例；先打磨数据页和复杂技术页，再检查整册。
3. **P2：完成比较与迁移。** 运行固定条件评测；依据证据清理旧内容，同步 registry、schema、校验器、链接、README 和 AGENTS 中的路线与目录约定。

发布前检查独立安装可用性和所有仓库质量门，不接受通过修改 baseline 掩盖迁移缺陷。当前仅交付方案；未删除旧素材、修改 skill 行为或提交代码。
