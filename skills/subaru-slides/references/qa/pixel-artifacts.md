# 渲染图像素缺陷（Pixel Artifacts）

> 这份 reference 只解决一件事：**交付前，用像素而不是眼睛，找出"乱样式"**。
> 适用于任何路径的产物——原生 PPTX、AI 底图、HTML deck——因为它们最终都被渲染成 PNG。

## 为什么需要它

几何检查读的是 **XML 属性**：框在不在页内、字号够不够、连接线斜不斜。
它看不见"渲染出来长什么样"，所以下面这些缺陷会整批漏过去：

- 文字在固定框里被压扁，或多出一个孤立的巨型数字；
- 两个色块交界处横穿一条细带，看起来像悬空的竖线；
- 边缘被裁掉的字、被撑大的孤字。

这些只在**像素**里可见。规则很简单：**先渲染成 PNG，再对 PNG 过一遍检查**。

## 三层防线

| 层 | 做什么 | 抓什么 | 抓不到什么 |
|---|---|---|---|
| 几何 | 宿主的 PPTX 检查（本仓库内是 `validate_pptx.py`） | 越界、占位符、字号下限、斜连接线、等尺寸节点 | 渲染后的观感 |
| **像素** | `scripts/detect_pixel_artifacts.py` | 换行孤字、超大字号、色带切割 | 设计意图（"谁盖住谁"） |
| 人眼 | 本文件末节的 60 秒清单 | 语义错误、审美判断 | 逐页一致性（看多页会疲劳） |

自动检查是**估算**。交付时要写清哪一项**没做**（claim boundary），不要声称做过视觉验证却没做。

## 运行

```bash
# 随本 skill 一起分发，零依赖（标准库），只读，不联网
python3 scripts/detect_pixel_artifacts.py renders/          # 全部检测器
python3 scripts/detect_pixel_artifacts.py renders/ --json   # 机读
python3 scripts/detect_pixel_artifacts.py slide-03.png --detail
python3 scripts/detect_pixel_artifacts.py --doctor          # 列出检测器与已知局限
```

整页约 1–2 秒。背景色取**全图众数色**，所以带截图外框、窗口边框的图也能正确处理。

算法只有一份：不要把它复制成第二份脚本。宿主若已有统一报告格式，包装它即可。

## 检测器

### 默认启用（判据可测、在真实版面上误报低）

| id | 判据 | 典型症状 | 修法 |
|---|---|---|---|
| `wrapped-numbers` | 一个墨块在上一组基线**下方 80px 内**另起基线，且水平区间与之重叠 | `8-10` 变成 `8-1` / `0`；孤字被放大 | 放宽文本框宽度、关掉 shrink-to-fit，或拆成两个对象 |
| `oversized-glyph` | 同一基线上，某字高 ≥ 邻字中位数 **3 倍**（且 ≥80px） | 孤字被 autofit 撑大 | 同 `wrapped-numbers`；检查 `normAutofit` |
| `band-cut` | 一条 ≤40px 宽的直带**贯穿**一条足够长的两色硬边界（两侧色场各 ≥150px） | 悬空细线、色块接缝处的碎线 | 删掉多余的描边/分隔矩形；对齐两色块的 z-order |

### 明确不做（写进 claim boundary）

这三条都**试过并主动删掉**，因为误报会淹没真缺陷：

- **不做"连线被图形盖住"**：像素里"被盖住"和"正常终止在图形边缘"是同一个现象——
  z-order 只存在于构建脚本，渲染图里读不出来。改成生成侧铁律（见下表）＋ 人眼清单；
- **不做**斜率/基线检测：中文字形笔画本身就会横向漂移 5–10px，做了只会淹没真正的缺陷；
- **不做** OCR、不做语义：不认识字，只看几何与颜色；**不是渲染器**，不模拟字体替换
  （跨机保真另见 `../typography-cjk.md`）。

## 逐页 60 秒人眼清单（自动检查补不上的那一半）

对**每一页原尺寸**确认（不要看 contact sheet）：

- [ ] 连线两端都**真的**接在节点上：没有"线扎进卡片里"，也没有三角箭头浮在线的旁边；
- [ ] 箭头用的是构建器的**端点箭头**，不是一个横放的三角形（见 `../layout-grammar.md`）；
- [ ] 每个数字/单位组都待在一行里：`8-10`、`3.5%`、`2024Q1` 没有被拆开；
- [ ] 框内文字没有被压扁、缩排或换行到框外；
- [ ] 高亮/强调对象确实框住了它要强调的东西，而不是压在别的元素上；
- [ ] 边框与底色交界处没有意想不到的细线或断口。

## 缺陷库 → 生成侧预防（比事后检测更根本）

| 生成时的做法 | 会产生的乱样式 | 正确做法 |
|---|---|---|
| 用三角形/图片"画"箭头 | 箭头与线错位、颜色不一致、被线穿过 | 用连接线的终点箭头属性（`headEnd` / `tailEnd`） |
| 连接线画在卡片**之后**（z-order 在上） | 线穿过卡片、被卡片边缘切断 | 先画线再画卡片，或把线锚定到卡片边缘 |
| 文本框过窄 + `normAutofit` | 数字组换行、孤字被放大 | 按最长一行留宽；显式换行；不依赖自动缩放 |
| 卡片边缘再叠一个描边矩形 | 细带穿色块、双重边框 | 用形状自身的边框 |
| 分割线用斜的/手画的 | 基线错位、看似弯曲 | 正交分隔线，对齐网格基线 |
| 中文与拉丁数字混在同一 run | 字体回退导致基线跳变 | 数字用显式字体；见 `../typography-cjk.md` |

## 修复顺序

1. 先改**生成脚本**里的几何与 z-order（`../layout-grammar.md`），不要只改渲染结果；
2. 重新渲染，重跑检测器直到只剩人为判断项；
3. 全册跑一遍，挑出**同一缺陷重复出现**的页——那通常是一条模板级规则错了；
4. 在交付 receipt 里写明：跑了哪些检测器、哪些 opt-in 没跑、哪些页只做了人眼检查。
