# 语义审阅约定

逐项解释行为如何满足或违背 case 的 criteria，不检查固定措辞、标题或关键词次数。
尽可能让审阅者不知道 baseline/skill 标签；独立审阅和自评应分别报告。

| 维度 | 看什么 | 不足以证明什么 |
|---|---|---|
| 遵循任务 | 数量、一次交付、评价时机、最新要求 | 使用了正确标题不代表遵循任务 |
| 思路差异 | 机制、场景、对象、问题定义的变化 | 同义改写或技巧名不代表新方向 |
| 分支保留 | 两条路线都继续、来源和编号保持 | 把两个词放进同一个方案不代表保留冲突 |
| 人参与 | 用户选择与贡献影响后续材料 | 大量助手输出不代表合作质量 |
| 建议与纠结 | 同时回应建议请求和未解决关切，后续选择依用户偏好而定 | 给出结论不自动等于过早收敛；末尾附一句问题不自动等于充分探索 |
| 转述与推测 | 用户立场、对方说法、未知与助手建议清楚区分 | 引用第三方承诺不代表其内容已获本人确认 |
| 恢复准确 | 已决定和未决定分开、当前分支正确 | 声称记得不代表恢复正确 |
| 能力诚实 | 文件保存、实验、访谈与搜索声明符合实际 | 提供一条路径不代表写入成功 |

数量可人工计数；近似点子是否仅改写需看具体机制。
每项判断引用 transcript 的助手原文，引用完整相关回复也可以说明缺失行为。
如果信息不足以判断，补充审阅或运行证据，不先填 true。
单次失败可定位具体规则，但不要把每次失败扩写为普遍限制。

在带纠结的建议案例中，看用户的矛盾是否影响分析和条件式选择，不规定问题数量或固定顺序。
用户明确只要结论时应直接交付；继续发散或强制问答同样是不符合任务。
多轮中用户补充关切时，应重新探索而非重复说服；先前的助手建议不等于用户已经决定。

对照解释应列出出现变化的案例、失败原因、重复运行稳定性及未控制条件。
只报告观察，不从“skill 多了几个点子”推导创新效果；语义审阅本身也需要复核。
